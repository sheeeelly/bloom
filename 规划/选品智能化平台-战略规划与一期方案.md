## 一、背景（压缩）

### 1.1 服装电商运营的日常选品链路（贴合当前项目）

服装电商的日常选品，本质不是“找几张竞品图”这么简单，而是围绕**本周什么值得上、为什么上、以上什么形态上**做一轮高频判断。公开行业实践通常都会把这件事拆成三类连续动作：先看市场和竞对，再看社媒与用户偏好，最后回到自家历史销售与退货验证；我们的现状也基本一致，只是这些动作仍分散在 Excel、截图、PPT 和多个系统里。

结合当前项目，业务实际链路更接近下面这条：

1. **周度找款与看盘**：品类运营先看竞品雷达周报、上新/下架变化、价格带、颜色和款式特征，再补看社媒热词、达人内容和站外热度，形成“市场在推什么”的初判。  
2. **内部验证**：拿候选款或候选属性去对照公司内部历史数据，判断类似颜色、廓形、领型、面料、袖型在 BD/AT 里是否卖得动、退货高不高、当前覆盖够不够，形成“我们能不能做、值不值得扩”的二次判断。  
3. **组织成提案**：运营把外部趋势、内部验证、价格建议、参考图和风险说明整理成提案，当前载体可能是 PPT，也可能是选款系统草稿。  
4. **进入选款链路**：提案在选款 1.0 中按 `草稿 → 一审 → 终审 → 打板` 推进，打板后生成 `goods_id`，作为后续生产、刊登、数据回流的主键。  
5. **对齐上新与刊登**：上海运营仍需按「上新要求表」向中山提需；打板/生产后，属性、图片和主键再进入刊登链路。《AI自动刊登》已梳理出精品路线 `板房素材 → AI 清洗/换装 → 双人审 → 推盘古`，试点优先 **BD**。

因此，本项目不是从零发明一个“选品工具”，而是要把运营已经在做的这条链路产品化：把**竞品雷达、社媒线索、内部历史验证**整理成一份能直接进入选款系统、并能继续衔接上新要求表与刊登链路的结构化方案。

### 1.2 当前痛点（按运营工作流展开）

| 环节 | 痛点 | 在当前项目中的具体表现 |
|------|------|------------------------|
| 市场扫描 | 信息看得到，但不能直接转成方案 | 竞品雷达已经能出 AT/BD 周报和三 Sheet 实表，但运营仍需手工挑图、抄链接、摘价格、拼截图 |
| 趋势判断 | 外部热度与内部可做性是两张皮 | 竞品/社媒告诉我们“市场在推什么”，但内部历史数据还没稳定进入提案层，导致“外部热、内部弱”与“内部强、外部冷”难以系统化区分 |
| 特征复用 | 属性口径不统一，历史经验难复用 | 同一面料、领型、廓形在竞品描述、内部属性、提案文案里的写法不一致，审核时难横向比较，也不利于后续沉淀 |
| 提案生成 | 方案产出依赖人工拼装 | 运营需要在竞品周报、社媒截图、内部报表、上新要求表、选款创建页之间来回切换，结果是准备慢、结构不稳定、审核阅读成本高 |
| 提交流转 | 提案内容与选款/上新表未完全同构 | 选款 proposal 字段、上海上新要求表、运营常用 PPT 不是一套结构，导致同一份判断要重复搬运两到三次 |
| 下游衔接 | 上游没把“后续要用的主键和证据”提前留好 | 刊登链路强依赖 `goods_id` / `ddid` 及属性、参考图、来源佐证，但上游提案阶段还没有统一留痕与回传结构 |

一句话概括：现在的问题不是“没有数据”，而是**外部竞品、社媒热度、内部历史验证都存在，却没有以运营日常决策顺序被整合成可直接提审、可追溯、可继续流转的选品方案**。

### 1.3 需求价值

全链路：`竞品/内部/舆情 → 方案中枢 → 选款 → 打板(goods_id) → 上新要求表/中山 → 自动刊登 → 盘古 → 销售回流`

| 优先级 | 价值点 | 状态 |
|--------|--------|------|
| P0 | **链路可追溯（上游→提案）**：竞品/内部/舆情三信号写入 `signal_refs` 与佐证，选款审核及事后仍可复盘「当时为何推/不推」 | 🔄 本期实现（`signal_refs` 100%） |
| P0 | **知识可流转（提案→选款）**：中枢方案留档留痕并与选款 proposal 合并，避免 PPT/Excel/系统间断档，形成可沿链路复用的选品知识库雏形 | 🔄 本期实现（选款留档 ✅；中枢溯源 🔄） |
| P1 | **断点提效（信号→方案→选款）**：打通竞品周报、内部报表、上新要求表、创建提案之间的手工搬运，周选会前找数/对齐时间目标缩短 50%+（基线待测） | 🔄 本期实现 |
| P1 | **风险前置（舆情→提案）**：PDL/差评在进选款/打板前进入 risk 维与避雷榜，减少「外部热但尺码/质量/图货有问题」流入下游 | 🔄 本期实现 |
| P1 | **绩效可归因（选款→打板→销售回流）**：`goods_id` 关联上架后销售/退货，量化品类运营选品贡献与方案命中率 | ⏳ 不在本期 |
| P2 | **全链可问数**：聊天跨链路查询本周机会、内部是否验证、有无避雷及后续表现 | ⏳ 不在本期 |
| P2 | **产能可见（提案→版房）**：版房 quota 与提案/打板队列联动，排期对运营与中山透明 | ⏳ 不在本期 |
| 后段 | **刊登可接续（goods_id→自动刊登→盘古）**：打板主键与提案字段带入刊登任务，减少刊登侧重复录入，衔接精品路线 BD 试点 | ⏳ 非本期关门项 |

**本期关门**：P0 两行 + P1 前两行——即**上游信号进提案、提案进选款**；绩效、问数、排期、刊登为链路延伸项，后置不写入 MVP 承诺。

### 1.4 产品目标

| 目标 | 说明 | 优先级 |
|------|------|--------|
| **三信号统一归集** | 竞品雷达（三 Sheet）/ 内部建议引擎报表 / 社媒线索 / 舆情避雷统一入库，属性映射到盘古 `md_attribute_dict`，禁止各子系统私造第二套口径 | P0 |
| **机会总览** | 选品工作台机会池：按业务线/周次/品类展示候选特征、四维分数、建议动作（主力/小测/回避/内部扩产） | P0 |
| **信号融合解析** | 竞品 trend + 内部适配度/四象限 + 舆情 PDL 风险交叉校验；冲突显式写入佐证，不静默抹平 | P0 |
| **方案一键生成** | 输出对齐上海上新要求表 + 选款「创建提案」字段；`signal_refs` 100% 可追溯 | P0 |
| **选款草稿同步** | 一键写入选款 `draft`，打标 `generation_source=system_hub`，幂等键 `hub_draft_id` | P0 |
| **舆情风险注入** | 商品 PDL 一二级原因自动带入 risk 维与提案佐证（Size/Quality/图货不一致等） | P1 |
| **内部引擎 API 拉取** | 替代 P0 人工上传 XLSX，按业务线+周期+属性实时查适配度与建议清单 | P1 |
| **智能问答** | 聊天框查「本周 BD 什么色在升、内部是否验证、有无避雷」 | P2 |

### 1.5 统一数据模型 · `selection_signal_records`（三信号统一）

竞品 SKC 行、内部属性排行行、社媒/舆情片段在入库时归一为同一张信号表，供机会池打分与方案生成消费。

```sql
CREATE TABLE selection_signal_records (
  id                  BIGINT       NOT NULL AUTO_INCREMENT,
  signal_source       VARCHAR(32)  NOT NULL  COMMENT 'competitor_radar/internal_engine/social/risk',
  data_week           VARCHAR(16)  NOT NULL  COMMENT '2026-W27',
  category_line       VARCHAR(16)  NOT NULL  COMMENT 'BD/AT/JP/WD/PROM',
  category            VARCHAR(64)  NULL      COMMENT 'Bridesmaid Dresses/Atelier/...',
  -- 竞品雷达（对齐三 Sheet 表头，禁止私增列名）
  site_name           VARCHAR(64)  NULL      COMMENT '网站名',
  brand               VARCHAR(64)  NULL      COMMENT '品牌',
  skc_key             VARCHAR(128) NULL      COMMENT '商品唯一键/SKC Key',
  spu_key             VARCHAR(128) NULL      COMMENT '款式 ID/SPU Key',
  product_url         TEXT         NULL      COMMENT '商品链接',
  list_type           VARCHAR(32)  NULL      COMMENT 'original_sort/new/delisted',
  rank_pos            INT          NULL      COMMENT '排序/下架前排序',
  rank_change         VARCHAR(32)  NULL      COMMENT '排名涨跌',
  price_sale          DECIMAL(10,2) NULL     COMMENT '售价',
  price_market        DECIMAL(10,2) NULL     COMMENT '标价',
  main_image_url      TEXT         NULL      COMMENT '主图',
  color_name          VARCHAR(128) NULL      COMMENT '颜色名称',
  detail_text         TEXT         NULL      COMMENT '商品详情描述',
  new_type            VARCHAR(64)  NULL      COMMENT '上新类型（上新表）',
  new_time            DATETIME     NULL      COMMENT '上新时间',
  delist_time         DATETIME     NULL      COMMENT '下架时间',
  crawl_time          DATETIME     NULL      COMMENT '爬取时间',
  -- 属性（映射 md_attribute_dict 后写入）
  attr_dimension      VARCHAR(32)  NULL      COMMENT 'Color/Silhouette/Neckline/Fabric/...',
  attr_value          VARCHAR(128) NULL      COMMENT '盘古枚举值',
  attr_combo_json     JSON         NULL      COMMENT '属性组合，如 {"Color":"Dusty Sage","Silhouette":"A-Line"}',
  -- 内部引擎（《内部数据选品建议引擎 PRD》）
  internal_fit_score  TINYINT      NULL      COMMENT '内部适配度 0-100',
  quadrant            VARCHAR(32)  NULL      COMMENT '重点机会/成熟优势/风险冗余/持续观察',
  coverage_skc        INT          NULL      COMMENT '当前覆盖 SKC 数',
  suggestion_id       VARCHAR(64)  NULL      COMMENT '建议编号',
  suggestion_action   VARCHAR(64)  NULL      COMMENT '扩配色/精简SKC/维持/...',
  trend_direction     VARCHAR(16)  NULL      COMMENT '上升/稳定/下降',
  -- 舆情/风险（复用商品 PDL 口径，与舆情系统对齐）
  pdl1_category       VARCHAR(32)  NULL      COMMENT '商品一级原因',
  pdl2_category       VARCHAR(32)  NULL      COMMENT '商品二级原因',
  risk_summary        VARCHAR(512) NULL      COMMENT '避雷摘要/差评摘录',
  -- 社媒（P1 字段名待后台确认）
  social_platform     VARCHAR(32)  NULL      COMMENT 'TikTok/Instagram/Pinterest/...',
  social_keyword      VARCHAR(128) NULL      COMMENT '热词/话题',
  social_heat_score   TINYINT      NULL      COMMENT '热度代理分',
  -- 融合输出（中枢写入）
  trend_score         TINYINT      NULL      COMMENT '外部趋势维 0-100',
  internal_score      TINYINT      NULL      COMMENT '内部验证维 0-100',
  gap_score           TINYINT      NULL      COMMENT '缺口维 0-100',
  risk_score          TINYINT      NULL      COMMENT '风险维 0-100',
  composite_score     TINYINT      NULL      COMMENT '加权综合分',
  suggested_action    VARCHAR(32)  NULL      COMMENT '主力候选/小测/回避/内部扩产',
  conflict_flags      JSON         NULL      COMMENT '如 ["外热内弱","外热内冗余"]',
  signal_ref_id       VARCHAR(256) NULL      COMMENT '溯源键，如 2026-W27|SKC Key',
  extra_json          JSON         NULL      COMMENT '导航栏字段/色列表/差评原文/关联 SKC 等',
  ingested_at         DATETIME     NOT NULL,
  PRIMARY KEY (id),
  KEY idx_week_line (data_week, category_line),
  KEY idx_source_skc (signal_source, skc_key),
  KEY idx_attr (category_line, attr_dimension, attr_value)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='选品三信号统一记录表';
```

**设计属性口径（与内部引擎 / 刊登属性对齐）**

| 属性维度 | 英文 | 竞品侧来源 | 内部引擎 |
|----------|------|------------|----------|
| 颜色 | Color | 雷达「颜色名称」 | ✓ |
| 廓形 | Silhouette | 详情描述解析 | ✓ |
| 领型 | Neckline | 详情描述解析 | ✓ |
| 面料 | Fabric | 详情描述解析 | ✓ |
| 后背 | Back Style | 详情描述解析 | ✓ |
| 袖型 | Sleeves | 详情描述解析 | ✓ |
| 裙摆/拖尾 | Hemline/Train | 详情描述解析 | ✓ |

**商品风险 PDL 口径（risk 维 · 与舆情系统复用）**

| 一级原因 | 二级原因（节选） | 选品 risk 用途 |
|----------|------------------|----------------|
| Style 款式问题 | 领口太低、开衩太高、版型不好… | 跟款/改版提示 |
| Size 尺码问题 | 尺码偏小、偏大、码数不合适 | 码型/小测决策 |
| Quality 质量问题 | 质量不满意、拉链/肩带/缝纫… | 回避或工艺说明 |
| Not-as-pictured 图货不一致 | 颜色/款式与图不一致 | 参考图/复色风险 |
| Material 面料问题 | 面料薄透、与色卡/样衣不一致 | 面料选型 |
| Customer 客户问题 | 改变主意、选错款式/颜色… | 低权重，一般不挡提案 |
| Wrong-item-received 发错货 | 发错商品/颜色/尺码 | 供应链侧，提案 risk 备注 |
| Logistics 物流/履约 | 送达超 DW、延迟 | 非选品主维，可忽略 |
| Others 其他 | 其他问题 | 兜底 |

### 3.1.1 竞品预测的整合与呈现原则

参考行业成熟产品的公开表达方式，竞品预测不宜只展示“抓了多少竞品”或“有多少张图”，而应按运营决策顺序呈现为三层：

1. **信号汇总层**：把竞品上新、排名变化、价格带、颜色/面料/廓形等属性趋势，与社媒热词、内部历史验证放在同一问题框架里。  
2. **洞察判断层**：不是平铺原始数据，而是输出“哪些属性在升温、哪些站点在推、哪些内部已验证、哪些存在退货/差评风险”的结构化结论。  
3. **业务动作层**：把洞察直接落到可执行动作上，例如主力候选、小测、回避、改版说明，并同步进入选款草稿与上新要求表形态。

因此，我们在“竞品预测”相关章节中统一采用下面的呈现逻辑：

| 呈现层 | 我们怎么写 | 对应输出 |
|--------|------------|----------|
| 市场发生了什么 | 竞品站点上新/下架/排名升降，按品类、价格带、属性聚合 | 趋势摘要、候选池 |
| 为什么值得关注 | 外部热度是否持续，内部适配度是否验证，舆情/退货是否提示风险 | 四维分数、冲突说明 |
| 该怎么行动 | 主力跟进 / 小测 / 回避 / 内部扩产 | 提案草案、上新要求表、选款草稿 |

这意味着“竞品预测”在本项目里的定位不是做一个独立看板，而是做成**提案前的趋势洞察与信号整合入口**：前面看趋势，后面直接出方案。

**内部适配度（0–100）· 中枢 `internal` 维主输入**

```text
内部适配度 = 销量表现×30% + 动销率×20% + 加购率×15%
           + 收藏率×10% + 趋势表现×15% + 低退货表现×10%
```

六子项先归一化 0–100 再加权（权重可在引擎设置调整，总和 100%）。含义：

| 子指标 | 作用 |
|--------|------|
| 销量表现 | 卖了多少（总量） |
| 动销率 | 铺货里真正在动的比例（效率） |
| 加购率 | 购买意向领先信号 |
| 收藏率 | 意向强度（弱于加购） |
| 趋势表现 | 近 N 周环比/同比方向与强度 |
| 低退货表现 | 过滤「卖得多但退得多」的虚假热 |

**四象限 · 与提案动作映射**

横轴：当前覆盖 SKC 数；纵轴：内部适配度。默认阈值：适配度 **70**、覆盖 **12 SKC**（空档地图页可调）。

| 象限 | 条件 | 提案中枢建议动作 |
|------|------|------------------|
| 重点机会 | 高分 × 低覆盖 | **主力扩产候选**（扩配色/尺码/关联款）；竞品若同步热 → 双高确认 |
| 成熟优势 | 高分 × 高覆盖 | 维持；外部跟款时作「内部已验证」强佐证 |
| 风险冗余 | 低分 × 高覆盖 | **回避或改版**；即使竞品热也标冲突，默认小测或不跟 |
| 持续观察 | 低分 × 低覆盖 | 不主动推；竞品热则标「外热内未验证→小测」 |

**六步链路（引擎产出 → 中枢只读消费）**

主键关联（`external_goods_id` + color）→ 指标聚合 → 趋势 → 适配度打分 → 象限 → **建议+证据链**（禁止无 SKC 依据编造）。

**中枢消费的 3 张核心报表（禁止私造列名）**

| 表 | 用途 | 关键字段（节选） |
|----|------|------------------|
| ② 属性钻取排行表 | 按维度查 Top 属性值 | 属性维度/值、销量、动销/加购/收藏/退货率、覆盖 SKC 数、趋势、**适配度总分+6 子项贡献**、象限 |
| ④ 选品建议清单表 | 运营待处理动作 | 建议编号、属性、象限、建议类型（扩配色/精简 SKC/…）、证据摘要、处理状态 |
| ⑤ 关联 SKC 明细表 | 佐证下钻 | SKC、`external_goods_id`、销量/加购/收藏/退货原因、上架时间 |

整包导出时另含 ① 概览摘要、③ 象限变动（**P1 未实现**，周对周迁移暂人工对照两期排行）。

**特征对齐规则（雷达 × 内部）**

从雷达行解析出的 Color / Silhouette / Neckline / Fabric 等，映射到盘古 `md_attribute_dict` 枚举后再查内部排行表：

1. 命中**单属性值**或**属性组合**行 → 取 `内部适配度` 与 `象限` 写入草案。  
2. 多属性命中时取 **min(适配度)** 作保守 internal 分，象限取「最差」优先级：风险冗余 > 持续观察 > 重点机会 > 成熟优势。  
3. 映射失败 → `internal` **留空**，佐证写「内部未匹配，待人工补」；不静默填 0 分。  
4. 雷达行「网站名/品牌 = Azazie」→ 可同时查内部 SKC 明细作**本站对照**，不作竞品热证据（同 §3.3.2）。

### 3.3 分析整合规则（大致、可解释）

#### 3.3.1 四维（权重默认，标定前可调）

| 维 | 含义 | 主要输入 |
|----|------|----------|
| trend | 外部是否在推 | 雷达：上新表命中、原始表「排名涨跌」升、排序靠前 |
| internal | 内部是否验证过 | **内部引擎**：属性钻取排行「适配度」+ 象限；建议清单动作 |
| gap | 相对缺口 | 竞品热 + 内部「重点机会/低覆盖」；或盘古 AZ 对比 gap；否则人工标 |
| risk | 差评/退货等 | AT 雷达差评列；内部「风险冗余」+ 退货率；舆情 L1 |

默认权重：trend 0.30 / internal 0.30 / gap 0.20 / risk 0.20。  
**internal 分映射**：直接采用内部适配度 0–100；缺失时该维不参与加权（其余维按比例归一），并在佐证显式标注「内部未接入」。

#### 3.3.2 三信号 × 四象限 · 场景动作

| 竞品 trend | 内部象限/适配度 | 舆情/退货 risk | 动作 | 选款 source_type 提示 |
|------------|-----------------|----------------|------|------------------------|
| 热（上新/排名升） | 重点机会 ≥70 | 低 | **主力候选** | Competitor（主）+ 内部段佐证 |
| 热 | 成熟优势 | 低 | 跟款/加色，内部已验证 | Competitor |
| 热 | 弱/空/<70 | 中低 | **小测** | Competitor；内部段写「未验证」 |
| 热 | 风险冗余 | 任意 | **回避或改版** | Competitor；冲突写入 risk |
| 热 | 任意 | 高（雷达差评/舆情/高退货） | 回避 | 同上 |
| 冷 | 重点机会 | 低 | **内部驱动扩产**（非跟款） | **Internal Data** |
| 冷 | 成熟优势 | 低 | 长青维持，不强跟外部 | Internal Data / Original |
| 仅 AZ 本站行 | 任意 | — | 不作竞品主证据 | Internal Data 或对照备注 |

冲突（外热内弱、外热内冗余）**必须**写入 `source_evidence` 与 `signal_refs`，不得静默抹平。

#### 3.5.2 提案佐证富文本模板（Competitor）

按创建页「品牌名+链接+截图」要求，中枢生成 HTML/富文本至少包含：

1. 数据周次：`{数据周次}`  
2. 品牌/网站：`{品牌}` / `{网站名}`  
3. 链接：`{商品链接}`  
4. 主图：嵌入或附「主图」URL（作截图等价物；运营可换本地截图）  
5. 排序与涨跌：`排序={排序}`，`排名涨跌={排名涨跌}`（上新表写上新类型/时间）  
6. 价格：`售价={售价}`，`标价={标价}`  
7. SKC：`{商品唯一键 / SKC Key}`  
8. 一句话结论 + 建议动作（主力/小测/回避）  
9. 若有差评列：摘录风险  
10. **内部交叉（有则必填）**：统计周期、匹配属性、适配度、象限、建议类型、建议编号（链到 SKC 明细）

`signal_refs` 示例：`type=competitor_trend`，`ref_id={数据周次}|{SKC Key}`，`url={商品链接}`；内部见 §3.2.2。

#### 3.5.2b 提案佐证片段（Internal Data · 内部驱动提案）

当 `source_type=Internal Data`（竞品冷、内部重点机会）时，佐证至少含：

1. 统计周期 `{period}`  
2. 属性维度/值 `{attr}`  
3. 内部适配度 `{score}` 与六子项贡献摘要  
4. 象限 `{quadrant}` + 系统建议动作  
5. Top 关联 SKC（≤5）及销量/退货摘要  
6. 与竞品关系说明（无竞品热 / 仅作价位参考）

#### 3.5.3 同步接口约定（与选款草稿）

- 动作：创建选款 `draft`（等价运营打开「创建提案」保存草稿）。  
- 幂等：`hub_draft_id`。  
- 失败：中枢保留草案，提示缺必填（如面料「待补」时：允许存草稿；**提交一审**仍按选款现网校验）。
